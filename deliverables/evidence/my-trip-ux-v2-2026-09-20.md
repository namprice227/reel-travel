# My Trip UX v2 implementation — 20 September 2026

The user approved the [five-screen proposal](../../docs/design/my-trip-ux-v2/README.md) and requested implementation. This change covers My Trip. The screenshots below use fictional fixtures and intercepted imagery/maps, not verified travel recommendations. No credentials, private uploads or real account records are included.

## Result

- `/my-trip` and `/my-trip/all` share a compact **My trips / Overview / All trips / Create trip** toolbar. Decorative introductory copy is removed. Existing Figtree controls and Newsreader trip names are retained with a tighter hierarchy and bounded images.
- All Trips keeps dates and planning status visible on phones. Upcoming includes future drafts. Search accurately describes trip/destination matching, sort is explicit, and browser return preserves URL filters/search/sort and list scroll.
- **Edit day** sits beside the selected day. Edit mode exposes Done, Undo and saving feedback. Rejections appear beside the day; no successful save is claimed before a response. Moves now have Undo. Fixed reservations retain their lock and have no move/remove controls. Regenerate remains under More in edit mode and in the stale-input banner.
- Selected-place order is linked title, provider hours for the itinerary date, **Full details**, address, map, directions and saved-source evidence. Unknown hours remain unknown. Fictional fixtures are labelled and do not receive canonical Google venue links. Full details retains day/stop context; browser Back restores the stop-list scroll.
- Below 1100px, selection opens a modal sheet. Close/Escape, focus containment, focus restoration, background scroll locking and nested notes are handled. The sheet animates for 180ms and respects reduced motion. The false drag handle is removed.
- My Trip map callers explicitly use Google. Selection focuses the corresponding saved coordinates and `hl=en` requests English. Stops without coordinates show a missing-location state instead of another stop's map. Whole-trip browsing follows chronological days; day navigation opens externally. Existing public/shared map presentation is retained.
- Current-day grouping and default itinerary day use the trip timezone. Trips outside their date range initially open day 1.

## Assumptions and remaining limits

- English is requested for maps based on the user's complaint about Japanese map display. This does not translate venue names or guarantee Google's label language.
- The existing coordinate iframe is reused without exposing a browser key or adding provider calls. It shows one selected location. Custom in-map multi-stop pins/route lines and a supported keyed Google renderer are deferred. Day routes open in Google Maps; Google's URL waypoint/platform limits still apply. Official references: [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started), [Embed API](https://developers.google.com/maps/documentation/embed/embedding-map). The existing keyless web iframe is not represented as the documented keyed Embed API.
- Live Google tiles, account configuration, attribution rendering, holiday hours and production deployment were not verified. Frames preserve Google's available display area; loading/delay fallback links stay accessible. Cross-origin frame errors cannot all be detected by the parent application.
- Hours summarize the current weekly provider contract for the selected date; visit fit uses the saved planner result. Travel durations remain estimates. No venue facts were invented.
- User approval covers the design and implementation request. Human review of the implemented UI, screen-reader testing, usability metrics and production acceptance remain pending. The earlier Canva upload was not retried.

Reproduce browser checks with a separately installed Playwright module. On this machine, `PLAYWRIGHT_EXECUTABLE_PATH=C:/Program Files/Google/Chrome/Application/chrome.exe`; the module defaults to `.local/browser-tools/node_modules/playwright/index.mjs`. The optional native run requires the local application and development sign-in; it creates only fresh synthetic test records and stubs all travel-provider requests.
